# Ear-training web app — audio and notation research

Research date: **2026-09-22**. All version numbers, publish dates, download counts, star counts and bundle sizes below were pulled live on that date from the npm registry API, the npm downloads API, the GitHub REST API, jsDelivr and Bundlephobia. Figures that are estimates rather than measurements are explicitly flagged as such. The review of `adrian729/thalia` was done by reading actual file contents through the GitHub contents API, not by inference.

## 1. What this document answers

This is the write-up of two research passes, driven by two concrete questions about building an EarMaster-style ear trainer (intervals, chords, scales, rhythm dictation) as a React web app.

**Question A — audio.** Is the Web Audio API on its own enough for this, and is there something worth adding to make it integrate more cleanly with React? Or is "React + raw Web Audio API", the approach already taken in the author's existing project [`adrian729/thalia`](https://github.com/adrian729/thalia), good enough to build on? Section 2 answers the sufficiency question and lays out the library options as genuinely competing choices; section 3 is a concrete, file-level review of thalia against the requirements of an ear trainer.

**Question B — notation.** How do you render sheet music and notes in React, and what packages exist on top of Canvas/SVG for this? Section 4 covers the notation engines (VexFlow, abcjs, OpenSheetMusicDisplay, Verovio, alphaTab), the hand-rolled SVG/Canvas option, React piano-keyboard components, and the commercial embeds.

Section 5 combines both halves into a recommendation matrix for a few named scenarios. Two framing points up front, because both recur throughout: **there is no single winner in either half of this research**, and in both cases the right answer depends on which exercise types the app actually ships. Statements below that read like recommendations are judgment calls with stated reasoning, not settled facts.

## 2. Audio: is raw Web Audio enough?

### 2.1 Short answer

**Yes for the sound-producing half. For the timing half, yes for most ear-training exercises and no for a specific minority of them, where you must write a ~60-line scheduler yourself.**

The structural insight that makes raw Web Audio genuinely viable here: almost every ear-training exercise is a **short, finite, fire-and-forget phrase** of at most a few seconds — an interval, a block chord, an arpeggio, a cadence, a two-bar rhythm. Every source node's `start()`/`stop()` takes an **absolute time in `AudioContext` clock seconds**, and every `AudioParam` has `setValueAtTime` / `linearRampToValueAtTime` / `exponentialRampToValueAtTime` / `setTargetAtTime` which also take absolute times. So the entire question can be scheduled in one synchronous burst at `ctx.currentTime + epsilon`, sample-accurately, with **no JS timer involved at all**:

```js
const t0 = ctx.currentTime + 0.1;                              // small offset so t0 is in the future
playNote(440, t0, 0.5); playNote(660, t0 + 0.6, 0.5);          // melodic interval, sample-accurate
[261.63, 329.63, 392.0].forEach(f => playNote(f, t0, 1.2));    // block chord, guaranteed simultaneous
[261.63, 329.63, 392.0].forEach((f, i) => playNote(f, t0 + i * 0.18, 0.4));  // arpeggio
```

This is fundamentally easier than the DAW/sequencer/looper use case that makes people reach for Tone.js's Transport. An ear trainer is closer to "play this 3-second sound" than to "run a loop at 120 BPM indefinitely." That is the single strongest argument that raw Web Audio suffices.

### 2.2 The caveats, in order of how much they will bite

**(a) Scheduling — needed only for the looping subset.** `setTimeout`/`setInterval` fire on the main thread and are delayed by layout, paint, GC, React reconciliation and network callbacks — **"tens of milliseconds or more"** of jitter (Chris Wilson, ["A Tale of Two Clocks"](https://web.dev/articles/audio-scheduling)). Already-scheduled audio plays perfectly; the problem is that *new* scheduling decisions arrive late. The canonical fix is a lookahead scheduler with the article's values — **100 ms lookahead, 25 ms timer interval**:

```js
function scheduler() {
  while (nextNoteTime < ctx.currentTime + 0.1) { scheduleNote(currentStep, nextNoteTime); advance(); }
  timerId = setTimeout(scheduler, 25);
}
```

The detail people get wrong: `nextNoteTime` must **accumulate** (`nextNoteTime += secondsPerStep`), never be recomputed from `ctx.currentTime` each tick — recomputing is exactly what produces cumulative drift. The timer can be moved off the main thread with a `Worker` running `setInterval` and `postMessage`-ing ticks (Wilson's `metronomeworker.js` pattern), or, in 2026, an `AudioWorklet` used as a clock.

You need this only for: a **metronome count-in** before a rhythm question (though a count-in plus pattern is still finite and can be one burst), a **looping drone/backing** while the user answers (a looped `AudioBufferSourceNode` with `loop = true` is free and needs no scheduler), **rhythm performance/clapback** exercises where the user taps along over a click for 8+ bars (this genuinely needs a running transport), and **mid-phrase tempo changes** (rare; usually you just regenerate the phrase). **Severity: low-to-medium.** Roughly 60 lines, well-trodden, easy to unit-test.

**(b) Gesture unlock and iOS suspend/resume — the one that will actually hurt.** All modern browsers create an `AudioContext` in `state === 'suspended'` if constructed outside a user gesture. Chrome/Edge auto-resume on the first genuine gesture (since ~M71), so lazy apps "just work" on desktop Chrome by accident — do not rely on it. **Safari (macOS and iOS) requires `ctx.resume()` called synchronously inside a real gesture handler** (`click`, `touchend`, `pointerdown`, `keydown`); a `resume()` from a promise continuation or a `setTimeout` after the gesture silently fails to unlock. The belt-and-braces priming pattern (playing a 1-sample silent buffer inside the gesture) is still recommended by [Matt Montag's writeup](https://www.mattmontag.com/web/unlock-web-audio-in-safari-for-ios-and-macos), though modern Safari usually no longer needs it.

**The failure mode is silent.** On iOS, `decodeAudioData()` resolves, `createBufferSource()` succeeds, `start()` returns, `onended` fires — and you hear nothing, with no error anywhere (see [WebAudio/web-audio-api#790](https://github.com/WebAudio/web-audio-api/issues/790)). Always assert `ctx.state === 'running'` before claiming readiness, and put a "tap to enable sound" gate in the UI.

iOS Safari also has a **non-standard fourth state, `'interrupted'`**, entered when the tab is backgrounded, the screen locks, a call comes in, or another app grabs the audio session. It does **not** return to `'running'` on its own — you must call `resume()` ([#2585](https://github.com/WebAudio/web-audio-api/issues/2585), [W3C TAG design-review #1069](https://tag-github-bot.w3.org/gh/w3ctag/design-reviews/1069)). If the context was `'suspended'` when the interruption happened it does *not* transition to `'interrupted'`, so both paths need handling. Practical fix: listen to `visibilitychange` **and** `ctx.onstatechange`, and `resume()` on every foreground transition.

**Severity: medium.** About 20 lines of code, but 20 lines that are the #1 cause of "works on my laptop, silent on my phone." Note that **Tone.js does not remove this problem** — `Tone.start()` is the identical unlock, just with one obvious documented entry point.

Other iOS specifics worth knowing: the **hardware ringer/silent switch** can suppress Web Audio output from Safari and is undetectable from JS (needs an FAQ line); **`sampleRate` coercion** between 44100/48000 depending on hardware and Bluetooth profile, which can change mid-session when AirPods connect; Safari refusing `OfflineAudioContext` with >10 channels or sub-44100 rates; `AudioWorklet` being internally shimmed over `ScriptProcessorNode` in some Safari paths; and **~150–250 ms Bluetooth output latency**, which is catastrophic for tap-along exercises and needs `ctx.outputLatency`/`ctx.baseLatency` compensation or a calibration screen. That last one is a product problem, not a library problem — no library solves it.

**(c) Node-leak hygiene.** Per spec a finished `AudioScheduledSourceNode` with no remaining JS references is collectible, and Chrome/Firefox do reclaim them. The two real leaks in practice are **downstream nodes you still hold** (a per-note `GainNode` connected to the master bus and never `disconnect()`ed keeps a graph edge alive; stash it in a ref or Map — which React code invariably does — and it lives forever) and **`ConvolverNode`s with their impulse-response `AudioBuffer`s**, which are megabyte-scale per instance. Hundreds of orphan nodes noticeably degrade audio-thread performance on mobile. The discipline that fixes ~95% of it is one line per voice: **`source.onended = () => chainTail.disconnect()`**, plus a single long-lived master/FX bus created once at module scope rather than per component.

Related and non-negotiable: **do not create more than one `AudioContext`.** Browsers cap them (Chrome historically at 6 per document, and hitting the cap throws). React StrictMode double-mounting an effect that does `new AudioContext()` is the classic way to burn the budget in development.

**(d) Timbre.** A synth-oscillator ear trainer sounds like a 1982 ringtone next to EarMaster's sampled piano, and this is pedagogically load-bearing, not cosmetic: recognizing a major third between two triangle waves is a measurably different — easier, less transferable — task than recognizing it on a piano timbre with real partials. This argues for a sampled instrument regardless of which scheduling path is chosen.

### 2.3 Verdict on raw Web Audio: sufficient, with an asterisk

The asterisk is not about capability. It is about how much of Tone.js you end up re-implementing. A realistic raw-Web-Audio ear trainer needs: a note-scheduling helper, an ADSR envelope helper, a polyphonic voice allocator with voice stealing, a lookahead scheduler for the metronome/loop cases, a context-unlock manager, an instrument abstraction so you can swap sine → sampled piano later, and a sample loader with caching. That is roughly **600–900 lines of infrastructure that is exactly what Tone.js already is**. The counter-argument is that all of it is boring, well-documented, dependency-free, fully typed by the browser's own TS lib, adds 0 KB to the bundle, and is code you fully understand when something breaks at 11pm.

**Tone.js.** Healthy: `Tonejs/Tone.js` has 14,732 stars, **58 open issues**, last push 2026-09-16, not archived, MIT, 798 published versions. An open-issue count of 58 against 14.7k stars indicates real triage. **Watch the tag split:** `npm install tone` gets you the ~17-month-old 15.1.22, while active development continues on `tone@next` (15.2.0 in 2025-05, 15.3.0 in 2025-09, 15.4.0 in 2026-01, 15.5.0 in 2026-02, and a cluster of 15.5.37–15.5.42 on 2026-09-15/16). The README states the policy explicitly: pre-release versions labelled `tone@next` published from passing dev-branch builds. Decide deliberately which tag you are on.

What it concretely solves for this app: `Tone.Transport` (a real musical timeline with `bpm`, `timeSignature`, `scheduleRepeat`, `scheduleOnce`, loop points, and musical-time notation like `"4n"`, `"8t"`, `"1:2:0"` — for rhythm dictation this is a genuine win, since a pattern is `["0:0:0", "0:1:0", "0:1:2", …]` instead of BPM→seconds arithmetic everywhere); `Tone.PolySynth` (voice allocation and stealing for free — `synth.triggerAttackRelease(["C4","E4","G4"], "2n", time)`); `Tone.Sampler` (multisampled instrument with automatic pitch-shifting between sample points — give it `{"C4": "C4.mp3", "F#4": "Fs4.mp3", "A4": "A4.mp3"}` and it interpolates the rest, which is the pragmatic path to a piano timbre); `Tone.Part`/`Sequence`/`Pattern`; `Tone.Time`/`Tone.Frequency` conversions; `Tone.Draw` for syncing visuals to audio events (useful for lighting up a piano key as the note sounds); `Tone.start()` as one documented unlock entry point; and exposed latency knobs (`lookAhead`, default 0.1 s, plus `updateInterval` and `"balanced"`/`"interactive"`/`"playback"` presets).

Costs: **74.8 KB gzipped** is the headline objection, and tree-shaking helps less than you would hope — Tone's internal module graph is highly interconnected (the Context/Transport/Draw singletons pull in a lot), so expect **40–60 KB gzip even for minimal usage**, not 10 KB. Unpacked size 5.4 MB. It depends on `standardized-audio-context ^25.3.70` and `tslib`, so "Tone vs standardized-audio-context" is a false choice — adopting Tone gives you the polyfill layer anyway. Bus factor is effectively one maintainer (Yotam Mann). The opinionated global Transport fights you if you ever want two independent timelines. And you will use maybe 20% of the API surface.

**Howler.js.** 25,352 stars, **418 open issues**, last push 2025-11-23, no release in **three years**. That combination is the signature of a widely-used, feature-complete, effectively frozen library: it still works, it is not being developed. **Wrong tool here regardless of maintenance:** Howler's API is `sound.play()` — **there is no "play at time T" parameter.** Timing is JS-timer-based, i.e. exactly the drift problem. You cannot express "play these three notes simultaneously, sample-accurately," and you cannot synthesize, so every note of every instrument in every octave must be a file (or one sprite, which reintroduces the timing problem since sprite offsets are handled in JS). Reasonable role: UI sounds (correct/incorrect dings, button clicks) decoupled from the music engine. That is arguably its only role here.

**use-sound.** Excellent React ergonomics — a real hook with proper cleanup, StrictMode-safe, and a clever lazy-load trick (1.8 KB in your bundle, pulling ~9 KB of Howler asynchronously after first render, since no audio can play before a user interaction anyway). Its README describes the project as **"semi-maintained"**; 3,154 stars, last push 2025-06-10. It inherits every Howler limitation: **no scheduling primitive whatsoever**, no synthesis, no real polyphony control. The `playbackRate` escape hatch technically lets you transpose one sample (rate = 2^(semitones/12)) but produces chipmunk/molasses artifacts beyond ±5 semitones, and two `play()` calls can never start on the same sample frame. **Garnish, not engine.**

**smplr.** Hit **1.0.0 on 2026-06-13** after 51 versions; 323 stars, **1 open issue**, MIT, **zero runtime dependencies**, full TypeScript types, 22.6 KB gzip. Same author as `soundfont-player` and `tonal` (danigb). Ships `Sampler`, `Soundfont`, `Soundfont2`, `SplendidGrandPiano`, `ElectricPiano`, `DrumMachine`, `DrumAbuse`, `Mallet`, `Mellotron`, `Smolken`, `Versilian`, with samples hosted on GitHub Pages — **no server setup, no assets in your repo**, which is a real convenience for a GitHub-Pages-hosted app. **Crucially, it schedules:** `instrument.start({ note: "C4", time: ctx.currentTime + 0.5, duration: 1.2, velocity: 80 })`, with `time` and `duration` in seconds against `audioContext.currentTime`, working directly against a plain `AudioContext` with no Tone.js dependency. It also has `await instrument.ready`, an `onLoadProgress` callback for a loading bar, a shared `SampleLoader` so multiple instruments don't re-fetch, and a `CacheStorage` wrapper so returning users don't re-download megabytes of piano. **This is arguably the highest-leverage single dependency in this research**: it solves the one thing raw Web Audio cannot solve cheaply — sounding like a real instrument — without imposing a framework. Main cost is the sample download (a good piano is several MB, and the GitHub Pages CDN has variable latency).

**soundfont-player** is **archived** (repo last push 2023-05-16; npm 0.12.0 from 2020-01-27), with the author pointing at `smplr` as the successor. Still downloaded ~3,875/week by inertia. **Do not start new work on it**; if a tutorial uses it, mentally substitute `smplr`. Related: **`webaudiofont`** (v3.0.4, 2022-06-28, ~2000 GM instruments, 5.5 MB unpacked) is **GPL-3.0-or-later**, which is a serious consideration for a hosted web app; smplr's MIT is cleaner.

**standardized-audio-context.** 779 stars, 15 open issues, last push 2026-09-01 (still actively worked even though the last npm publish is 2024-08-31), 482 versions, MIT, baseline Chrome 105+/Firefox 113+/Safari 17.3+. Its most compelling argument is types that, per the README, *"actually match the concrete implementation"* — versus TS's built-in DOM lib types, which are generated from the Web IDL and describe things browsers do not actually implement. **Verdict: probably skip standalone.** The 26 KB gzip buys protection against edge cases an ear trainer will never hit (you are playing oscillators and buffers, not writing a worklet DSP chain); you get it free if you adopt Tone; and the one Safari problem you *will* certainly hit — the `'interrupted'` state and gesture unlock — is **not** something it solves.

**React wrappers: there is no credible, maintained, general-purpose React↔Tone.js binding.** The ecosystem is `use-sound` (Howler-based, wrong tool), a scattering of abandoned `react-tone`/`tone-react` experiments with single-digit stars, and `react-music` (dead since ~2017). The React-Three-Fiber-style "declarative renderer for an imperative library" model has never been done successfully for audio, for a defensible reason: audio graphs are long-lived, stateful and latency-sensitive, and reconciling them to a render tree fights the medium. **The community pattern is hand-rolled hooks, and that is the right answer.** The non-negotiable rules that fall out of React 18/19 StrictMode's deliberate double-mount: (1) the `AudioContext` is a **module-level singleton**, created once, never closed, never owned by a component; (2) audio nodes live in refs, never in state; (3) every effect that creates a node returns a cleanup that disposes/disconnects it, mirroring setup exactly; (4) **never fire an audio side effect from inside a `setState` updater** — StrictMode double-invokes updaters, which double-triggers the note.

### 2.5 Music theory: adopt `tonal`

This is the least controversial recommendation in the entire document. `tonal` 6.4.3 (2026-01-18), 4,238 stars, 43 open issues, last push 2026-07-28, TypeScript-native, pure functions, **14.1 KB gzip** for the full meta-package — and it is a monorepo of ~23 independently published scoped packages (`@tonaljs/note`, `interval`, `chord`, `scale`, `key`, `mode`, `voicing`, `voice-leading`, `roman-numeral`, `progression`, `range`, `midi`, `pcset`, `abc-notation`, `rhythm-pattern`, …), so importing only what you need lands well under that.

**Package-name caveat:** the modern package is **`tonal`** (v6.x). The older scoped meta-package **`@tonaljs/tonal` is stuck at 4.10.0 from 2023-01-12** and should not be used for new work; many stale tutorials reference it. Minor note: the GitHub repo record carries no SPDX license field, though the packages themselves declare MIT in `package.json` — worth a 30-second verification before committing, but it is universally treated as MIT.

Why it is close to purpose-built for this app: `Note.midi("C4")`, `Note.freq("A4")`, `Note.transpose("C4","P5")`, `Note.enharmonic`, `Note.simplify` kill the need for hand-maintained note tables entirely. `Interval.distance("C4","G4") // "5P"`, `Interval.fromSemitones(7)`, `Interval.semitones("m3")`, `Interval.invert` are exactly the interval-exercise domain model, **including the compound and enharmonic cases** (augmented 4th vs diminished 5th) that are pedagogically important and painful to hand-roll. `Chord.detect(["D","F#","A","C"])` is *directly* the answer-checking function for a chord-identification exercise, and `ChordType.all()`/`ScaleType.all()` enumerate qualities for quiz generation. `Key.majorKey("C")` gives the full diatonic chord set and secondary dominants — instant cadence exercises. `Progression.fromRomanNumerals("C", ["I","IIm7","V7"])` is the functional-harmony exercise directly.

The item most worth highlighting: **`Voicing.get("Cmaj7", ["E3","A4"], VoicingDictionary.lefthand)` plus `VoiceLeading.topNoteDiff`.** Playing every chord as a root-position stack of thirds makes chord-quality training trivially easy *for the wrong reason* — students learn the register, not the quality. Randomized voicings and inversions with sane voice leading are what make the exercise real, and this is the thing you would otherwise never build. And **`@tonaljs/rhythm-pattern` v1.0.0** gives a principled random-rhythm generator instead of `Math.random()` soup: `binary(13) // [1,1,0,1]`, `hex("8f")`, `onsets(1,2,2,1)`, `random(len, prob)`, `probability([…])`, `rotate(pattern, n)` and **`euclid(8,3) // [1,0,0,1,0,0,1,0]`** (Euclidean/Bjorklund rhythms). It is a thin, newish module — you will still want your own duration/tie/rest layer on top for notated rhythm dictation — but it is a good seed.

**`teoria.js`: do not use in 2026.** Latest 2.5.0 from **2017-07-02**, last commit 2019-12-01, last tagged release v0.4 in 2014, no TypeScript types, and dependencies on a constellation of the author's equally dormant micro-packages (`daccord`, `helmholtz`, `interval-coords`, `pitch-fq`, `scientific-notation`). Its chainable OO API (`teoria.note('a4').interval('M3')`) reads nicely and it has a duration model and Helmholtz notation that Tonal handles differently, but Tonal is a practical superset, typed, and alive. Know teoria exists only to recognize it in old Stack Overflow answers.

### 2.6 The three coherent audio stacks

These are genuinely alternative choices, not a ranking with one winner.

**Option A — raw Web Audio + `tonal` + `smplr`.** ~37 KB gzip of dependencies. Keep thalia's singleton engine and cleanup discipline, thread a `when` parameter through everything, write a ~60-line lookahead scheduler for the metronome/loop cases, and use smplr's `SplendidGrandPiano` for a real timbre (it takes `time` in `ctx.currentTime` seconds, so it drops in cleanly).

*Pros:* smallest bundle, total control, no framework opinions, everything typed by the browser's own lib, nothing to re-learn when debugging. Most defensible if the author enjoys the audio layer as an end in itself — which, given they wrote 579 lines of hand-rolled drum synthesis with explanatory comments, is plausibly the case here.
*Cons:* the most code by far; a real risk of reinventing Tone.js badly; rhythm dictation with tempo/meter/bars is where the hand-rolled path costs the most.

**Option B — Tone.js + `tonal`.** ~89 KB gzip. `Tone.Transport` + `Tone.PolySynth` + `Tone.Sampler` for audio, `tonal` for content generation.

*Pros:* fastest route to a working rhythm-dictation module; Transport's musical-time notation removes an entire category of arithmetic; voice allocation and multisampling are free; this is what the entire prior-art field converged on independently.
*Cons:* 74.8 KB gzip (realistically 40–60 KB even minimal); a single-maintainer dependency; the `latest`/`next` tag confusion; a learning curve in Transport time notation; you will use ~20% of the API.

**Option C — hybrid (Tone.js for the Transport/rhythm modules only, raw Web Audio + smplr for pitch modules). Considered and dismissed.** It sounds like the best of both, but it gives you **two context-management stories** — Tone owns a context, your raw code owns another — unless you carefully call `Tone.setContext(yourContext)` and keep that invariant forever. You then have two unlock paths, two cleanup disciplines, and two mental models for "when does sound happen," which is precisely the complexity the split was meant to avoid. Named here only to be dismissed.

**Unconditional, path-independent recommendations:** adopt `tonal` (near-free); add an explicit gesture-unlock plus `'interrupted'`-recovery layer before anything ships; use **sampled instruments, not oscillators**, for the actual exercises; and **thread absolute `when` times through every play function from day one**, because retrofitting it later touches every file.

Three observations that matter. **`vincentxu123/chord-ear-trainer` is the closest architectural match to what is being proposed here** — React 19 + `tone` + `tonal` + `zustand`, with progressions "synthesized on the fly with a sampled piano using Tone.js" (i.e. `Tone.Sampler`, not oscillators). That is essentially a working proof of Option B. **`WilsonNet/earvibes` is the useful counterfactual for thalia**: nearly identical base stack (React 19.2 + Tailwind 4 + clsx + tailwind-merge) with Tone added — it is what thalia's stack looks like after someone decided ear training was the goal. And **`geoffmyers/music-ear-trainer` adds `vexflow`** plus a Capacitor native wrapper, which signals both that notation rendering becomes necessary once you go past interval quizzes, and that going native sidesteps the iOS Safari audio problems entirely (at the cost of app-store distribution).

Worth naming as a non-React reference point: **musictheory.net**'s exercises historically used **pre-rendered audio sprites** rather than synthesis. That is a legitimate low-tech option — pre-render every note you need into one sprite file and schedule offsets, trading network weight for zero synthesis complexity. It only has the Howler timing problem if you play it through Howler; decode the sprite into an `AudioBuffer` yourself and use `start(when, offset, duration)` and you get **sample-accurate sprite playback**, which is a genuinely underrated raw-Web-Audio technique. The [`ear-training` GitHub topic](https://github.com/topics/ear-training) is the best browse point for more prior art.

### 2.8 Input-side notes (for later scope)

**Web MIDI**: Chrome 43+, Edge 79+, Opera and Samsung Internet ship it; **Firefox 108+ gates it behind a one-time "Site Permission Add-On" install prompt**, which is awkward UX; **Safari on macOS and iOS does not support it at all** and WebKit has declined to ship it for years on fingerprinting grounds. Consequence: MIDI-keyboard answering must be an *enhancement*, never the only input path, and it excludes essentially all iPhone/iPad users.

**Microphone / sing-back / pitch detection**: `getUserMedia` + `AnalyserNode.getFloatTimeDomainData` + a detector. **`pitchy` v4.1.0** (pure ESM, **7.8 KB min / 2.8 KB gzip**, McLeod Pitch Method, returns `[hz, clarity]`) is the lightest good option; `pitchfinder` offers YIN/AMDF/DynamicWavelet, is more configurable, and is heavier and less actively maintained. Neither is a complete "did the user sing the right interval" solution — you still need note quantization, hysteresis, onset detection and a confidence gate. **Budget real time for this; it is the single most underestimated feature in ear-training apps.**

**Rhythm tapping**: do not use `Date.now()`. Use the pointer/key event's `event.timeStamp` (same monotonic clock as `performance.now()`), correlate to audio time via a one-time `performance.now()` ↔ `ctx.currentTime` offset measurement, then subtract `ctx.outputLatency`.

## 3. Review: `adrian729/thalia` as a foundation

Repo: [github.com/adrian729/thalia](https://github.com/adrian729/thalia) — public, MIT, TypeScript, created 2025-02-16, **last push 2026-06-05**, 1,730 KB, 38 commits on main, deployed to GitHub Pages via `.github/workflows/gh-pages-deploy.yml` (`gh-pages -d dist`, base path `/thalia/`).

### 3.1 What it is today

A **browser synthesizer playground, not an ear trainer**: two 12-note chromatic melodic pads (`ThaliaPad`, keyboard-mapped, per-pad oscillator type across sine/square/sawtooth/triangle plus a joystick control), a 9-pad drum machine (`DrumPad`, number keys 1–9), a convolution reverb with four impulse responses (`public/IR/IR_church.wav`, `IR_basement.wav`, `IR_bathroom.wav`, `IR_pipe.wav`), and a live FFT spectrum visualizer (`Analyser`, `fftSize` 2048, canvas-drawn).

Stack from `package.json`: runtime dependencies are **`react ^19.2.0`, `react-dom ^19.2.0`, `tailwindcss ^4.0.6`, `@tailwindcss/vite ^4.0.6` — that is the entire list**. Dev: Vite ^6.1.0, TypeScript ~5.7.2, ESLint 9 flat config + typescript-eslint 8 + prettier 3.5.3, `gh-pages` ^6.3.0. Minor packaging bug: `clsx` and `tailwind-merge` sit in `devDependencies` but are imported by runtime code (Vite bundles them anyway, so the build doesn't break). **Zero audio libraries, zero music-theory libraries** — 100% hand-rolled Web Audio against the browser's own TS DOM types. Roughly 40 source files, ~2,400 lines of TS/TSX excluding the note table.

### 3.2 What it already gets right — keep all of this

**The module-scope `AudioContext` singleton (`src/audio-context/useAudioSetup.ts`).** A lazy module-level singleton:

```ts
let engine: AudioSetup | null = null;
export function getAudioEngine(sampleRate = 48000): AudioSetup {
  if (engine === null) {
    const audioContext = new AudioContext({ sampleRate });
    const mainNode = new GainNode(audioContext, { gain: 1 });
    mainNode.connect(audioContext.destination);
    engine = { audioContext, mainNode };
  }
  return engine;
}
```

carrying a comment that shows the author already understands the core React↔Web-Audio tension: *"The audio engine is a persistent, mutable singleton that lives OUTSIDE React's render/effect lifecycle. An AudioContext is a browser-limited, clock-bearing resource: it must survive StrictMode remounts and the whole page lifetime, so it is created exactly once and never closed."* `MainAudioContext.ts` goes further and wires `getAudioEngine()` as the React context's *default value*, so there is exactly one context whether or not the Provider is mounted. This is precisely the pattern §2.4 recommends.

**`useLazyRef` (`src/utils/useLazyRef.ts`)** — a 15-line helper that avoids the `useRef(new GainNode(...))` anti-pattern by constructing lazily on first render only. Used throughout `useReverb` and `useAnalyser`, again with a comment explaining why.

**StrictMode-aware cleanup.** `useReverb` (125 lines) splits dry/wet gains around a `ConvolverNode`, fetches and `decodeAudioData`s IRs on demand, and its `useEffect` cleanup explicitly `disconnect()`s all four edges with the comment *"Disconnect on unmount so a StrictMode remount (or a destination change) doesn't leave doubled routing edges feeding the bus."* `useKeyboard` (45 lines) dedups held keys via a `useRef<Set<string>>` with the comment: *"Track held keys in a ref (mutable, imperative) rather than state. The handlers fire audio side effects, so they must run OUTSIDE any setState updater: StrictMode double-invokes updaters, which previously double-triggered notes."* That comment is **direct evidence the author has already hit, diagnosed and fixed the exact React-19-StrictMode audio bug** described in §2.4 rule (4) — a meaningful signal about the foundation's quality.

**Anchored gain ramps and per-voice teardown (`useOscillator`, 126 lines).** `ATTACK = 0.01` / `RELEASE = 0.03` click-free ramps, with the ramp **anchored at the param's current value** (`gainNode.gain.setValueAtTime(gainNode.gain.value, ctx.currentTime)` before ramping), which is the correct way to avoid pops on retrigger; teardown on `oscillator.onended`; and `useEffect`s that live-update frequency/detune/gain on a held note. Clean, idiomatic, click-free.

**The hand-rolled drum synthesis (`src/utils/audio.ts`, 579 lines)** is legitimately competent DSP-by-hand and legitimately reusable for rhythm exercises: `playSynth` layers up to four oscillator types into one gain bus, and nine drum voices (`playKick`, `playSnare`, `playHihat`, `playTom1/2/3`, `playCymbal1/2/3`) are built from oscillators and filtered noise buffers with exponential envelopes — the kick is a 150 Hz oscillator with an exponential frequency sweep plus a noise transient; hi-hats are a bank of square oscillators through bandpass/highpass with a 0.02 s attack and 0.3 s decay.

Collectively this plumbing is above-average and was clearly arrived at by hitting the bugs, not by copying a tutorial. Anyone starting the ear trainer fresh would want to arrive at exactly this. **Port this layer.**

### 3.3 What is missing or risky at ear-trainer scale

1. **Everything plays *now*. There is no `when` parameter anywhere in `audio.ts`.** Every `play*` function opens with `const currentTime = audioContext.currentTime;` and schedules relative to that — `osc.start(currentTime); osc.stop(currentTime + duration)`. `useOscillator.start()` likewise starts immediately. That is exactly right for a playable instrument (press a key, it sounds) and exactly wrong for an ear trainer, whose core operation is *"play this sequence of (pitch, onset, duration) triples at these precise offsets."* **This is the single biggest refactor.** The fix is mechanical but pervasive: thread `when: number` through every `play*` function and every envelope call, then build `schedulePhrase(events, startTime)` on top. Until then, an arpeggio has to be `setTimeout`-driven and will audibly wobble; a block chord assembled from three separate `playSynth` calls reads `currentTime` three times (microseconds apart, so inaudible for chords — but the `setTimeout` path for arpeggios and rhythms is a real problem).

2. **No scheduler at all.** No lookahead loop, no transport, no BPM concept, no bar/beat model anywhere in the repo. Rhythm dictation, metronome count-ins and tempo-controlled melodic playback all need this built from scratch or delegated to `Tone.Transport`.

3. **Zero `resume()` calls — silently dead on iOS.** `grep` for `resume|suspend|'suspended'|interrupted|unlock|pointerdown|touchstart` across all source returns **zero hits in code**; the only matches are a comment in `useAudioSetup.ts` and a README line telling the user to *"click anywhere to unlock the audio context if prompted."* Worse, the `AudioContext` is constructed **eagerly at module-evaluation time** (it is the React context's default value, so it exists before any gesture can possibly have happened), which means it starts `suspended` in every browser. It works on desktop Chrome only because Chrome auto-resumes on the first gesture. **On iOS Safari this will be silently dead**, and there is no handling for the `'interrupted'` state either. For a laptop toy, fine; for an app people will use on a phone during a commute, this is a launch blocker. The fix is small — an explicit `resume()` in a gesture handler, a "tap to start" gate, and a `visibilitychange`/`statechange` re-resume — but must be done deliberately.

4. **Zero `disconnect()` and zero `onended` in `audio.ts` — node leak.** Verified by grep: `grep -c "disconnect" src/utils/audio.ts` → **0**. Every drum hit and every `playSynth` note creates a `GainNode` (and for drums, several `BiquadFilterNode`s and `AudioBufferSourceNode`s) connected to the destination bus and never torn down. In a drum pad hit a few hundred times this is survivable. In an ear trainer running thousands of exercises per session, especially on mobile, it becomes audio-thread bloat. Note the inconsistency: **`useOscillator` *does* clean up correctly** (`oscillator.onended = () => gainNode.disconnect()`), so the author knows the pattern — it simply was not applied to the fire-and-forget layer.

5. **Polyphony is per-component, not pooled.** Voices come from `useOscillator` instances bound to pad buttons; there is no central voice allocator and no voice stealing. A four-note block chord in an ear trainer is not four mounted components — it is one engine call. The current shape cannot express that.

6. **The 968-line hand-written note table (`src/utils/notes.ts`) is a liability.** It is 129 object literals from `{midiId: 0, frequency: 8.1758, name: 'C', octave: -1}` through midiId 128, each with `name`, `accidental` (♯/♮/♭ glyphs), `octave` and `pianoKey`. It encodes pitch/frequency/octave/key position but has **no concept of intervals, chord qualities, scales, keys, enharmonic spelling rules or voicings** — which is 100% of what an ear trainer needs in order to *generate* content. Extending it by hand to cover "generate a random minor 7th chord in second inversion in a comfortable tessitura, spelled correctly" is weeks of work that `tonal` does in one line. Hand-maintained tables also invite subtle bugs: **the midiId 128 entry with `octave: 9` is already past the MIDI spec's 0–127 range.**

7. **Sine/square/saw/triangle timbres are pedagogically weak** — see §2.2(d). Argues for `smplr` or `Tone.Sampler` regardless of scheduling path.

8. **Latency is uncalibrated.** No use of `ctx.outputLatency`/`ctx.baseLatency` anywhere. Irrelevant for a synth you play; fatal for rhythm clapback over Bluetooth headphones.

Also worth noting: `App.tsx` pulls `{audioContext, mainNode}` from context, renders an "Audio Context not ready!" fallback, then mounts `<Analyser>` + two `<ThaliaPad>` + `<DrumPad>`, and carries the author's own TODO: *"pass audioContext/state to components and remove the Context."*

### 3.4 Verdict: good bones, wrong shape

**Keep the plumbing; do not keep extending the architecture as-is.** The foundational React/Web-Audio hygiene is above average and is exactly what you would want. But the *domain model* is "an instrument you play in real time," whereas an ear trainer's domain model is "a scheduler that plays generated phrases at you and then grades your answer." Those need different centers of gravity, and the gap is not closed incrementally.

Concretely, the changes needed:

- **Keep:** `useAudioSetup` (module-scope singleton), `useLazyRef`, the ref-not-state discipline, the anchored gain ramps, `useOscillator`'s `onended` teardown, the explicit graph `disconnect()` on unmount, the keyboard-handler-outside-setState rule, and the drum synthesis in `audio.ts`.
- **Add a `when: number` parameter** to every `play*` function and every envelope call in `audio.ts`, plus a `schedulePhrase(events, startTime)` layer on top. Do this first — retrofitting it later touches every file.
- **Add the gesture-unlock layer**: explicit `resume()` inside a real gesture handler, a "tap to start" gate, a `visibilitychange` + `ctx.onstatechange` re-resume for the iOS `'interrupted'` state, and a `ctx.state === 'running'` assertion before declaring readiness.
- **Add `onended`-based `disconnect()`** to every fire-and-forget voice in `audio.ts`, matching what `useOscillator` already does.
- **Delete `notes.ts`** in favour of `tonal`'s `Note.freq()`/`Note.midi()`; keep the `pianoKey` mapping only if a specific UI needs it, and derive even that.
- **Replace oscillator timbres with sampled instruments** for the actual exercises (`smplr`'s `SplendidGrandPiano` or `Tone.Sampler`).
- **Introduce a pooled voice allocator** so a chord is one engine call, not N mounted components.
- **Then make a deliberate call** on Transport-vs-hand-rolled-scheduler (§2.6 Options A and B).

It is a fine *starting point* and a poor *architecture to keep extending* without that refactor.

## 4. Notation rendering in React

### 4.1 Two structural facts that apply to everything below

**None of the serious notation engines are React-native.** VexFlow, abcjs, OSMD and alphaTab are all imperative libraries that take a DOM element and draw into it. In every case the React integration is the same ~20–40 line pattern: a `useRef` on a container `<div>`, a `useEffect` that clears the container and re-renders on prop change, and a cleanup function. **There is no maintained React wrapper for any of them** — `react-vexflow` (0.0.4, 2019-07-09, 13 weekly downloads, targets the VexFlow 3/4 API), `react-abcjs` (0.1.3, 2020-01-21, 21 weekly downloads), `react-sheet-music` (0.0.1, 2020-03-06, 3 weekly downloads, depends on `abcjs@^5`); and `vexflow-react`, `react-vexflow-hooks`, `verovio-react`, `react-opensheetmusicdisplay` and `@coderline/alphatab-react` **do not exist on npm at all** (OSMD's and alphaTab's "React wrappers" are example repos or nothing). You will write that component yourself whichever engine you pick. Budget for it once and stop shopping.

**The one structural exception is Verovio**, which returns an SVG **string**, so its component is literally `<div dangerouslySetInnerHTML={{__html: svg}} />` — no refs, no imperative cleanup, no StrictMode footgun. That is the best React fit in the field, and it costs ~2.3 MB gzipped.

Three cross-cutting integration hazards, stated once:

- **StrictMode is the #1 integration bug** for VexFlow/abcjs/OSMD/alphaTab. The effect runs → cleanup → runs again in dev; without an `innerHTML = ''` guard (or equivalent remove-the-SVG-I-created cleanup) you get **two overlapping staves in dev and one in prod** — a maximally confusing dev-only bug.
- **Async-render race.** OSMD's `load()` and Verovio's WASM module init are async. In a fast quiz loop a stale effect can resolve after the next question is set and render the *previous* answer. Needs an `ignore` flag or `AbortController`. VexFlow and abcjs are synchronous and do not have this problem.
- **SSR.** All engines need a DOM; guard for Next.js (`dynamic(…, { ssr: false })`). Hand-rolled SVG and build-time Verovio are the only server-renderable options.

### 4.3 VexFlow

**First, a correction that will otherwise mislead a quick dependency audit: VexFlow is not abandoned, despite tooling saying so.** Snyk currently reports VexFlow as "Inactive"/"discontinued" on the basis of no npm release in 12+ months and no activity in the repo it scans. That verdict is wrong, because **the project moved repos**. `github.com/0xfe/vexflow` (4,386 stars, last push 2025-03-05) is the *old* repo and now holds only the **VexFlow 4.x LTS** line, published separately on npm as **`vexflow4`** (3,326 weekly downloads); its issue #1635 is literally titled "VexFlow Repository Has Moved >>>". The live repo is **`github.com/vexflow/vexflow`** (237 stars — low only because the move reset the count), **last commit 2026-09-16**, with recent work including "Make LICENSE machine readable" (2026-09-15) and "optional repeat brackets" (2026-08-02), maintained by Ron Yeh and Rodrigo Vilar.

The legitimate criticism is **release cadence, not abandonment**: npm `vexflow` is still at **5.0.0 from 2025-03-05**, so roughly 18 months of unreleased work sits on `main`. If you hit a bug fixed on `main`, you may wait or install from git. (Related trivia: GitHub's license detector reports `NOASSERTION` on the old `0xfe` repo because of a dual copyright block; the new repo is correctly detected as MIT, and the Sept 2026 machine-readable-LICENSE commit was specifically about fixing that.)

**Size — and the nuance everyone misses.** Bundlephobia reports `vexflow@5.0.0` at 1,097.9 KB min / **676.3 KB gzip**, 0 dependencies. That terrible gzip ratio is because the default bundle embeds music **font glyph outline tables**, which do not compress. But VexFlow 5 ships **three bundles**: `vexflow.js` (1,101.9 KB, all fonts), `vexflow-bravura.js` (711.1 KB, engine + Bravura), and **`vexflow-core.js` at 328.7 KB — engine only, no font payload**, with fonts loaded lazily at runtime via `VexFlow.loadFonts('Bravura', 'Academico')`. Individual ESM font modules: `bravura.js` 321.9 KB, `petaluma.js` 293.5 KB, `glyphs.js` 134.5 KB. So the realistic footprint is **~330 KB critical JS plus a ~320 KB deferred font fetch**. **Quoting the 676 KB Bundlephobia figure overstates VexFlow's weight by roughly 3x.** Note also that VexFlow is **not meaningfully tree-shakeable** — it is a class graph with heavy internal cross-references; the bundle split *is* the tree-shaking story.

**API, two levels.** High-level **Factory + EasyScore** makes generated snippets genuinely cheap — `score.notes('C#5/q, B4, A4, G#4', { stem: 'up' })`, chords as `'(C4 E4 G4)/w'`. For a generated interval or chord this is close to abcjs ergonomics, which is better than VexFlow's reputation suggests. The low-level API (Renderer/Stave/StaveNote/Voice/Formatter/Beam/Accidental) is where the "complex" reputation is earned and deserved: you wire a `Formatter` to a `Voice` against a `Stave`, construct `Beam`s yourself and call `Accidental.applyAccidentals()` yourself. **Rhythm dictation with beamed eighths and sixteenths puts you in that territory.**

**Pros:** most-used and best-known engine; good engraving; EasyScore is cheap for generated content; `vexflow-core` keeps critical bundle to ~330 KB; MIT; zero runtime dependencies; TypeScript-native (ignore `@types/vexflow`, it is a stub pointing at the real types); handles rhythm/beaming/tuplets properly when asked.

**Cons:** imperative-only with the StrictMode footgun; **awkward interactive hit-testing** — VexFlow's SVG output is *not* class-annotated the way abcjs's is, and the PR "Include class attribute when drawing stavenote and stem" has been open since 2025-10-26 and is still unmerged as of 2026-09-22, so click-to-answer means attaching listeners to generated SVG elements after `draw()` or overlaying your own invisible hit rects computed from stave geometry; 18-month release gap; and a confusing maintenance picture split across two repos and two npm packages (`vexflow` vs `vexflow4`) that will trip up any dependency audit.

### 4.4 abcjs

`abcjs@6.7.1` published **2026-09-21 — the day before this research**; repo `paulrosen/abcjs`, 2,349 stars, last push 2026-09-21, 252 open issues (high, but that is issue volume from an active single-maintainer project, not rot). MIT. 42,220 weekly downloads, essentially neck and neck with VexFlow. **Best release cadence of anything here** — 2026 alone: 6.6.2 (Feb), 6.6.3 (Apr), 6.6.4 (Jul), 6.7.0 (Aug), 6.7.1 (Sep).

**Content generation is the cheapest of any option.** ABC syntax makes an ear-training snippet a one-line template literal: chords/simultaneous notes are square brackets (`[CEG]` is a C major triad, an interval is just a two-note chord `[CE]`, a melodic interval is `C E`); durations are multipliers (`A2`, `A/2`) against `L:`; rests are `z`/`x`; accidentals are `^`/`_`/`=` (with `^^`/`__` for doubles); octaves are `,` and `'`; and the minimum header is just `X:1` plus `K:` — **`T:` (title) is optional and prints nothing if omitted**, which is exactly right for a snippet. So `"X:1\nK:C\n[CEG]"` is a complete, valid, title-less C major triad.

```
Interval (harmonic M3, C4–E4):   X:1\nK:C\nL:1/1\n[CE]|
Interval (melodic P5 ascending): X:1\nK:C\nL:1/1\nC G|
Chord (Am7):                     X:1\nK:C\nL:1/1\n[A,CEG]|
Scale (D major ascending):       X:1\nK:D\nL:1/4\nDEFG|ABcd|
Rhythm dictation (4/4):          X:1\nM:4/4\nL:1/8\nK:C clef=perc\nBB B2 BBBB|B4 B2B2|
```

**Beaming is implicit and automatic** — notes written without spaces beam together (`ABcd` beams, `A B c d` does not) — and accidental placement, key signatures and spacing are handled by the engraver with no calls from you. **For rhythm dictation this is a large practical advantage over VexFlow**, where you construct `Beam` objects manually. `K:C clef=perc` gives a percussion clef directly; `clef=none` gives a clefless staff.

**Two options make abcjs uniquely good for interactive ear training.** **`add_classes: true`** tags every drawn element with an identifying class (`abcjs-note`, etc.), so you can style, highlight, hide or animate individual notes with plain CSS and hit-test them trivially — **VexFlow cannot do this today**. And **`clickListener`** is a first-class callback fired when the user clicks a note or drags a selection, which **directly implements "click the note on the staff to answer"** with no geometry math; combined with `selectTypes` it is the best built-in interactive-input story of any library here. Other useful render options: `staffwidth` (default 740 — set small for a single-chord reveal), `scale`, the four `padding*` options to trim generous default whitespace, `responsive: "resize"` for fluid SVG in a React layout, `oneSvgPerLine`, and `ariaLabel`.

**Built-in audio is a genuine differentiator, with caveats.** `new abcjs.synth.CreateSynth()` → `.init({ visualObj, audioContext, millisecondsPerMeasure, options: { soundFontUrl } })` → **`.prime()`** (downloads/decodes and caches samples — **skipping `prime()` is the classic "no sound" bug**) → `.start()`. `abcjs.synth.SynthController` + `CreateSynthControl` give a drop-in transport UI (play/pause/loop/tempo/progress, styled by `abcjs/abcjs-audio.css`), and **`abcjs.TimingCallbacks`** drives a playback cursor synced to the rendered notation — combined with `add_classes`, that is a ready-made "play it back and watch the notes light up" feature. **But:** the default soundfont is fetched over the network from **`https://paulrosen.github.io/midi-js-soundfonts/FluidR3_GM/`**, a maintainer's personal GitHub Pages host, and it covers only **MIDI pitches 27–87**. **Self-host it and pass `soundFontUrl` for production** — relying on someone's GitHub Pages for your app's audio is an availability and latency risk. And the synth still needs a user gesture (the `init()`/`prime()` split exists partly so you can pre-buffer before that first click).

**Size and packaging caveats.** `dist/abcjs-basic-min.js` is **499.9 KB minified**; Bundlephobia failed to return a result on the research date, so there is **no measured gzip figure** — a reasonable estimate for 500 KB of minified JS with no embedded font blobs is **~120–150 KB gzipped, flagged as unverified**. `package.json` has `main: "index.js"`, **no `module` field, no `exports` map, no `sideEffects` flag** and no runtime dependencies (it does ship types at `types/index.d.ts`). Practical consequence: CJS-first, bundlers cope, but **tree-shaking is effectively zero** — you carry the parser, renderer, synth and editor whether you use them or not, and **there is no renderer-only build**. If bundle size is a hard constraint and you are not using abcjs's audio, `vexflow-core` at 330 KB beats abcjs at ~500 KB.

**Why abcjs is nonetheless the healthiest and easiest-to-integrate default for reveal-a-chord-on-a-staff use cases:** it has the best maintenance signal in the field (released the day before this research), the cheapest content generation, automatic beaming and accidentals, the only first-class click-to-answer and per-note CSS classes, rhythm support via `clef=perc`, and audio in the box — and its costs (500 KB with no tree-shaking, a third-party default soundfont to replace, CJS-first packaging) are all tolerable rather than blocking. abcjs's own FAQ confirms React works and **React Native does not** (it needs a real DOM to measure glyph widths before laying out SVG), and says to defer the call to client-side under Next.js/Nuxt.

### 4.5 OpenSheetMusicDisplay (OSMD)

`opensheetmusicdisplay@2.1.3`, published 2026-09-19; 1,970 stars, last push 2026-09-19, 79 open issues, **BSD-3-Clause**, 28,163 weekly downloads. Commercially sponsored by PhonicScore.com — a well-funded, actively developed project, not a hobby repo; 2026 saw 2.0.0 (Jun) through 2.1.3 (Sep), with 2.1.2's notes touting "~40% median speedup, 47% median for large scores." Size: 1,297.3 KB minified, **327.2 KB gzipped**, 5 dependencies.

**The elephant: OSMD is built on `vexflow@1.2.93`** — a pinned, nine-year-old VexFlow — alongside `jszip@3.10.1` (for `.mxl`), `loglevel`, `@types/vexflow@^1.2.38` and `typescript-collections`. PR #1700 ("Port OSMD to VexFlow 5 with stable engraving and explicit fonts") is open and unmerged. So adopting OSMD means shipping *a* VexFlow anyway, an ancient one, plus a full MusicXML parser and a full score-layout engine — to draw a two-note interval.

**Assessment: overkill, with one exception.** Rendering a single C major triad means generating a MusicXML document — `<score-partwise>` → `<part-list>` → `<score-part>` → `<part>` → `<measure>` → `<attributes>` (divisions, key, time, clef) → three `<note>` elements with `<chord/>` markers, each with `<pitch><step/><alter/><octave/></pitch>` and `<duration>`/`<type>`. That is **40–60 lines of XML for what ABC expresses as `[CEG]`**, plus an async parse-and-layout per question (and the stale-effect race that comes with `load()` being async). The exception is when you **already have MusicXML** or want real, existing, multi-measure scores: melodic dictation against a real excerpt, a sight-singing module fed by a public-domain MusicXML corpus, "identify the chord at bar 12." It also has a **Cursor API** (step through measures/notes), transposition, extensive `EngravingRules` for suppressing titles/part names/measure numbers, and even Braille music output. Its React "wrapper," `opensheetmusicdisplay/react-opensheetmusicdisplay` (49 stars, MIT, last push 2026-03-27), is **an example application, not an npm package** — copy the pattern. No audio at all; bring your own.

### 4.6 Verovio

`verovio@6.3.0`, published 2026-08-19; repo `rism-digital/verovio`, 929 stars, **last push 2026-09-22 — the research date itself**, 176 open issues. Written in **C++, compiled to WASM**, backed by RISM Digital (an academic musicology institution). 6,140 weekly downloads — the smallest audience of the majors, because its natural constituency is digital musicology, not app developers.

**Size is the disqualifier for a quiz loop.** `dist/verovio-toolkit-wasm.js` is 7,139.3 KB; `verovio-module-hum.mjs` (Humdrum build) is 12,084.8 KB; Bundlephobia measures **8,023.3 KB min / 2,349.2 KB gzipped**, 0 dependencies. **~2.3 MB gzipped** is between 5x and 20x every alternative. It can be lazy-loaded and code-split (module init is async anyway) so it need not block first paint, but a phone user still downloads multiple megabytes before the first reveal.

**Best React story of any engine, structurally**, because `renderToSVG()` returns a string: `const svg = useVerovio(mei); return <div dangerouslySetInnerHTML={{ __html: svg }} />`. No refs, no imperative cleanup, **no StrictMode duplicate-render footgun**, SSR-able in principle. The only structural requirement is that the expensive async WASM init must be a module-level singleton or React context, never per-component. Note `types` is `null` in the package — **no bundled TypeScript definitions**.

**Input formats blunt the usual "Verovio needs verbose MEI" objection:** it accepts MEI (native), MusicXML (compressed and uncompressed), **ABC**, **PAE (Plaine & Easie)**, Humdrum (with the `-hum` build) and DARMS. ABC means you can share an ABC generator with an abcjs implementation — a nice hedge — and PAE is a deliberately terse single-line encoding designed for incipits, arguably even more compact than ABC for a short generated snippet. Other capabilities: **best-in-class engraving** (scholarly-grade layout, full SMuFL support, Leipzig default with Bravura/Petaluma selectable), `renderToMIDI()`, and **`renderToTimemap()`** — a note-onset timemap, exactly what you need to sync an external Web Audio player to the rendered notation for highlight-as-it-plays. There is **no built-in synth**; bring your own audio.

**License caution.** **LGPL-3.0-or-later** — the only copyleft-ish license among the mainstream options. The usual reading is that dynamically loading an unmodified WASM module is analogous to dynamic linking and therefore acceptable without open-sourcing your app, provided you do not modify Verovio (or you publish your modifications), you include the license text and attribution, and the user remains practically able to substitute a modified Verovio. **However**, bundlers routinely inline and mangle the module into your app bundle, which muddies the "replaceable component" argument, and LGPL compliance in the JS-bundling world is genuinely unsettled. This is a real question for a closed-source commercial product and stands in contrast to the MIT/BSD-3 of everything else. **Not legal advice — a factor, not a verdict.**

**Where Verovio actually makes sense here: a build-time pipeline.** If the exercise bank is finite and known, run Verovio in Node **at build time** to emit static SVG strings for every question, ship those as data, and never load the WASM in the browser at all. That buys the best engraving in the ecosystem at **literally zero runtime cost**. This is the strongest argument for Verovio in this project and is easy to overlook.

### 4.7 alphaTab

`@coderline/alphatab@1.8.4`, published 2026-07-05, with **601 published versions** — extremely high release velocity; 1,846 stars, last push 2026-09-17, 60 open issues, TypeScript, 10,037 weekly downloads, **MPL-2.0** (file-level copyleft: using it as a dependency imposes nothing on your code, but modifying alphaTab's own source files means publishing those modified files under MPL-2.0 — much weaker than LGPL in practice, but not MIT).

Size: `dist/alphaTab.min.js` is **1,094.5 KB minified** (Bundlephobia returned nothing, so estimate ~250–300 KB gzipped, **unverified**) — but the JS is not the real payload. alphaTab also needs a **SoundFont2 file** for audio (it bundles a SONiVOX-derived SF2 from AOSP; GM SF2s in this class are typically **1–5 MB**) plus **Bravura and text fonts** as separate assets. The honest real-world footprint is **several megabytes**, comparable to Verovio, though most of it is deferrable.

Capabilities: imports Guitar Pro (gp3–gp7+), MusicXML, MIDI and Capella, plus **alphaTex**, its own compact text notation that is easy to generate programmatically (the ABC analogue — so the "cheap generated input" box is checked). It renders **both standard notation and tablature**, configurable per staff, and tab can be turned off entirely. **The headline is the built-in audio engine**: a full MIDI synthesizer (a port of TinySoundFont) running in an **AudioWorklet**, with layout and rendering pushed to background **WebWorkers**, giving you General MIDI instruments, tempo control, looping, a **metronome**, a **count-in**, per-track mute/solo, and a **playback cursor synced note-accurately to the rendered notation** — as one integrated system, with no glue code.

**Does that replace a Web Audio layer?** Genuinely, partly yes — it covers most of what an ear trainer needs from audio for score-shaped content. But three counter-arguments are real. **(1) You give up fine control**: ear training sometimes wants signal-shaped audio — a pure sine for interval discrimination, exact cent detuning for tuning exercises, a specific timbre, a precise gap between the two notes of a melodic interval. A MIDI-synth-plus-soundfont is the wrong abstraction for those, and raw Web Audio oscillators are trivially better. **(2) Everything must be expressed as a score** — to play a reference pitch or a chord the user has not yet seen notated, you must first construct a score object or alphaTex string, which is an awkward detour. **(3) Cold start**: loading the SF2 and spinning up the AudioWorklet before the first question is noticeable. Most EarMaster-style apps want both score-shaped and signal-shaped audio, which argues for a plain Web Audio layer as the primary engine anyway — at which point alphaTab's audio becomes redundant weight.

**Is the guitar orientation a limitation? Partly, yes.** The data model is guitar-first (`Track` → `Staff` with tablature as a first-class citizen, string/fret info, tuning, bends, slides, palm mutes), so a piano-style two-note interval means configuring away a lot of machinery; the docs, examples and community are overwhelmingly guitar/bass/tab-oriented (the React integrations found in the wild are all guitar tools: `gallegretti/escala`, `ElBeh/songlab`, several Chinese-language tab practice apps). It *can* render plain standard notation on a plain staff and that works, but you are steering a guitar engine to do it. **For a guitar-focused ear trainer (fretboard recognition, tab exercises, "which fret is this") alphaTab is unbeatable and the obvious choice.** For a general/keyboard-oriented one, it is a lot of engine pointed slightly the wrong way.

**React integration is officially unsupported** — alphaTab's own installation docs say verbatim that *"alphaTab doesn't provide yet an out-of-the box React control and integration"* and that developers must handle low-level DOM mapping themselves via refs; **there is no `@coderline/alphatab-react` on npm**. It also has integration friction unique to it: because it spawns background WebWorkers and AudioWorklets, it needs **real bundler configuration** — official Webpack and Vite plugins exist and are documented (which is more than the others offer), but alphaTab touches your build config in a way VexFlow and abcjs do not, and font/soundfont assets must be served from a configured path. The existence of a community repo literally named `matevzjecl/alphatab-react-font-error` tells you the font-loading-under-a-bundler problem is common. **Heaviest integration effort of all options.**

### 4.8 Hand-rolled SVG (and why not Canvas, and why not a drawing library)

Most comparisons skip this. For this specific app it is **a serious contender, not a fallback.**

An ear-training reveal is usually **one clef, one five-line staff, one bar, one to four noteheads, maybe an accidental, maybe a ledger line**. No justification, no beaming, no key-signature ordering, no multi-voice, no ties, no tuplets. That is not "music engraving," it is "draw some ellipses at computed y-coordinates" — a genuinely ~150–300 line React component. Pitch → vertical position is a pure function: map the note to a **diatonic step index** (C=0, D=1, E=2, F=3, G=4, A=5, B=6, plus 7×octave), then `y = baselineY - (stepIndex - clefReferenceStep) * (staffSpace / 2)`. Accidentals are a glyph offset to the left; ledger lines are drawn for every position beyond the staff at even half-step intervals. That is the whole algorithm.

**Sub-approach (a): pure geometry, zero dependencies.** Staff = five `<line>`s; notehead = `<ellipse rx≈6 ry≈4.5 transform="rotate(-20)">` (real noteheads are tilted ellipses); stem = a `<line>` up-right or down-left by staff position; ledger lines = short `<line>`s; clef = a hand-traced `<path>` lifted from a public-domain SVG, or omitted entirely in keyboard-centric designs. **0 KB of dependencies, ~200 lines.** Looks "clean and functional" rather than "engraved" — which at 200×120 px is frequently indistinguishable to the user.

**Sub-approach (b): SMuFL font + `<text>` glyphs — best quality-per-byte in the entire document.** Load **Bravura** or **Bravura Text** (Steinberg, **SIL Open Font License** — explicitly free to use, embed and redistribute including commercially) as WOFF2 and render real engraving glyphs as SVG `<text>` at their SMuFL codepoints: U+E050 `gClef`, U+E062 `fClef`, U+E0A4 `noteheadBlack`, U+E0A3 `noteheadHalf`, U+E0A2 `noteheadWhole`, U+E260 `accidentalFlat`, U+E261 `accidentalNatural`, U+E262 `accidentalSharp`, U+E4E5 `augmentationDot`, U+E014 `staff5Lines`, the U+E022 leger-line family, the U+E4E3 rest family, U+E1D5+ for individual notes with stems and flags. Two documented gotchas, both confirmed against the SMuFL/Bravura specs: **ledger lines are not automatic** — the standalone leger-line glyphs have *zero advance width*, so you emit them yourself before the notehead, raised or lowered by the same number of staff positions — and noteheads sit on the baseline at their staff position, so all vertical math remains yours. The font is the only real cost and it is controllable: full Bravura is a few hundred KB, but **subsetting to the ~20 glyphs you actually use** (`pyftsubset`/fonttools) typically yields **well under 20 KB (estimate)**. An order of magnitude smaller than any engine, with genuinely professional symbols.

**The React advantage is large and under-appreciated.** A hand-rolled staff is fully declarative — notes are JSX. Consequences: **no `useRef`, no `useEffect`, no imperative cleanup, no StrictMode double-render bug** (the entire class of integration bugs in §4.1 simply does not exist); **highlighting is a prop** (`<Note pitch="E4" state="correct" />` → a `className`, versus hunting an engine's generated SVG that does not even emit classes); **click-to-answer is `onClick` on a `<g>`** with no hit-testing or geometry math; **animation works** (Framer Motion or CSS transitions on individual noteheads, staggered reveals, a note sliding into place — impossible with an imperative engine that owns the DOM); **SSR-safe by construction**; and **perfect theming** via CSS variables, where getting an engine's SVG to match a dark theme is fiddly. A non-obvious extra benefit: your data model stays *your* note representation (MIDI numbers, or `{step, alter, octave}`), not an engine's string DSL, so you can add a second renderer later without restructuring anything.

**The honest boundary.** Hand-rolling stops being smart the moment you need **beaming** (beam angle/slope, beam breaking, secondary beams for sixteenths — genuinely hard, and *exactly* what rhythm dictation needs), **tuplets** (bracket placement, ratio numerals), **automatic horizontal spacing/justification** across mixed durations, **key signatures** with correct accidental ordering and octave placement, **multiple voices**, ties, slurs, dynamics, multi-measure content, or **cautionary-accidental logic** across a bar. These are precisely what notation engines exist for, and reimplementing them is a multi-week project that produces worse output than a 30-second install. **The line is roughly: pitch display → hand-roll; rhythm display → use an engine.**

That suggests a hybrid: hand-roll the staff for the 90% case (intervals, chords, scale degrees, single-note reveals) and **lazy-load a real engine behind the rhythm-dictation route only**, keeping the main quiz loop at zero notation dependencies without painting yourself into a corner.

**Not a drawing library.** D3, Konva, react-konva and Two.js all work mechanically, but music notation is a *positioning* problem, not a *drawing* problem — the hard part is the pitch→y math and glyph placement, which no drawing library helps with, and they add 30–150 KB to do what raw `<svg>` already does. **Plain SVG in JSX is strictly better.** **Canvas is also worse than SVG here**: no DOM nodes means no CSS, no per-note event handlers, no accessibility, manual `devicePixelRatio` handling, and redraw-on-every-change.

**The ecosystem is uniformly stale. This is the decisive fact.**

**`react-piano`** ships small (`react-piano.esm.js` 29.6 KB, UMD 110.9 KB, plus `dist/styles.css` 2.6 KB) with runtime deps `classnames`, `just-range`, `lodash.difference`, `prop-types`. It is class components + PropTypes era. **React 19 note:** React 19 removed `PropTypes` from the `react` package, but `react-piano` depends on the standalone `prop-types` package directly, so that specific breakage does not apply, and its `peerDependencies` of `react: "*"` means npm will never complain. Its 28 open issues are feature requests and Dependabot noise, **not compat reports**; the newest substantive ones are a 2024 PR adding CSS-variable customization and a 2024 question asking whether it can be used for visual highlighting. **Verdict: stale but probably still works.** The real friction is API shape: it is designed around *playing* (`onPlayNoteInput`/`onStopNoteInput`, `keyboardShortcuts`, `playNote`/`stopNote`). For highlighting a quiz answer you want the controlled **`activeNotes`** prop (an array of MIDI numbers) with no-op play handlers — it works, but you are using a play-oriented component in display mode, and the fact that someone had to file an issue asking whether that is possible tells you the docs do not lead with it. Styling is dated: an imported CSS file plus class overrides, no CSS custom properties (the PR adding them is unmerged), so theming it to a modern design system means fighting its stylesheet.

**`klavier`** has **zero runtime dependencies**, modern hooks-based TypeScript, inline styles, controlled `activeNotes`, custom key rendering and interactive input — **a strictly nicer API than `react-piano` for this use case**. Two problems: **23 weekly downloads** (essentially no adoption, so no battle-testing and no chance of a fix), and `peerDependencies` pinned to **`react ^18.2.0`**, which trips React 19 installs and needs `--legacy-peer-deps` or a `package.json` `overrides` entry. It almost certainly works at runtime on React 19 (hooks only, no legacy APIs), but you are opting into a warning on an unmaintained dependency. It is small enough that **forking or vendoring it is completely reasonable** — which is itself an argument that you may as well write your own.

**The recommendation nobody makes but should: write it yourself.** A piano keyboard is a *smaller* problem than a staff. White keys: 7 per octave, equal-width `<rect>`s (or flex children), index within octave = `[0,2,4,5,7,9,11].indexOf(pitchClass)`. Black keys: 5 per octave, **absolutely positioned** at fixed fractional offsets within the octave (after C, D, F, G, A), width ≈ 0.6× a white key, height ≈ 0.6× — a five-entry lookup table you write once. MIDI number ↔ key position is pure arithmetic. Total: **~150–200 lines of JSX + CSS**, zero dependencies, fully themeable with CSS variables, trivially highlightable and clickable, accessible (`role="button"`, `aria-label="C4"`), animatable. Given that every package here is stale, **the maintenance risk of a vendored 200-line component you own is lower than the maintenance risk of a 2019 dependency.** Use `klavier`'s source as a reference implementation.

**Why keyboard-only designs are attractive for ear training specifically** — worth treating as a first-class design option, not a footnote. **No notation literacy required**, which broadens the audience enormously (plenty of guitarists and producers train their ears without reading notation). **No enharmonic ambiguity**: on a staff C♯ and D♭ are different, on a keyboard they are the same key — and for interval/chord *quality* recognition the keyboard representation is actually more truthful to what the user heard. **Interval shape is visually obvious**: a major third is "4 keys apart," which is directly the thing being learned. **Input is unambiguous**: click keys → chord; no staff hit-testing, no accidental-entry UI, no clef choice. And **it is by a wide margin the simplest thing to build.** A design using a keyboard as the primary display and answer surface, with a small *optional* staff reveal for users who want it, is both the cheapest to build and arguably the better product for most learners.

### 4.10 Commercial embeds — why probably not

**Flat.io Embed.** `flat-embed@2.12.1` (2026-04-02), **Apache-2.0 for the *client*** (the *service* is not free); repo `FlatIO/embed-client`, 76 stars, last push 2026-09-21, 959 weekly downloads. Mechanically it is an `<iframe>` pointing at flat.io plus a `postMessage` JS/TS SDK that can `loadMusicXML()`/`loadJSON()` on the fly, control playback, move a cursor, transpose and switch into editor mode — so it *can* display generated scores. **Cost:** free on a personal/Community plan **with Flat branding and non-commercial use only**; Flat's docs say that customizing it (removing branding, changing controls/colors/theme) or using it commercially requires an embed plan, and **pricing is not published** — the documented path is emailing `embed@flat.io` for custom volume-based pricing. **Why probably not:** an iframe round-trip per question is slow and heavy for a loop that should be sub-100 ms; you are renting a third-party runtime for something you can render locally; no offline support; hard vendor lock-in on your core display layer; unpublished negotiated pricing is a bad fit for an indie app and makes cost unpredictable; and free-tier branding sits in the middle of your quiz UI. Worth knowing about only if the app later wants full user-facing score *editing*, which is genuinely expensive to build and is Flat's actual value proposition.

**Soundslice** — embed API with outstanding playback-synced notation, slicing/looping and a superb practice UX; commercial, contact-based pricing. Conceptually the closest of these to what an ear-training app wants, and correspondingly the most tempting — but the same lock-in and cost objections apply, and it is built for "practice along with this piece," not "identify this chord." **Noteflight** (Hal Leonard-owned) is the same category with the same objections. **MuseScore.com / Sheet Music Direct** embeds are *content catalog* embeds (play this published score), not rendering APIs. **SeeScore SDK** is commercial and mobile-first, not a web fit.

**Collective verdict:** every commercial option in this space is priced and designed around *displaying existing published scores* or *editing* them. An ear trainer does neither — it displays three notes it generated a millisecond ago. Paying a per-volume license for that is an obvious mismatch. Note them for completeness and move on.

### 4.11 Cross-cutting notation notes

- **Licenses at a glance:** VexFlow **MIT** · abcjs **MIT** · OSMD **BSD-3-Clause** · Verovio **LGPL-3.0-or-later** (compliance thought needed for closed-source commercial) · alphaTab **MPL-2.0** (file-level copyleft, mild) · Bravura font **SIL OFL** (free commercially) · `flat-embed` client Apache-2.0 but the *service* needs a paid plan commercially · `react-piano` and `klavier` **MIT**.

## 5. Recommendation matrix

Restating the framing, because it is a genuine conclusion rather than a hedge: **there is no single winner in either half of this research.** Three or four options are defensible for the same app, and the right answer turns almost entirely on which exercise types matter most and whether notation is the primary UI or an optional reveal. What follows are judgment calls with stated reasoning.

### 5.1 Notation choice by need

| Need | Primary suggestion | Strong alternative | Avoid |
| --- | --- | --- | --- |
| **Reveal a chord/interval/scale on a staff** — no rhythm, 1–4 notes, one bar | **Hand-rolled SVG staff + subsetted Bravura** (~20 KB, declarative, no StrictMode bugs, trivially themed/animated/clickable) | **abcjs** (~500 KB, one-line ABC strings, `add_classes`, `clickListener`, free audio) or **VexFlow via `vexflow-core`** (~330 KB + lazy font) | Verovio (2.3 MB for three notes), OSMD (whole score engine + 60 lines of XML per chord), alphaTab, any commercial embed |
| **Real rhythm notation** — beamed eighths/sixteenths, rests, tuplets | **abcjs** — automatic beaming from the string, `clef=perc`, `M:`/`L:` for meter, built-in synth + `TimingCallbacks` for a synced cursor | **VexFlow** — more control and engraving nuance, smaller core bundle, but you construct `Beam`s and apply accidentals manually | Hand-rolling (beaming is the wall) |
| **Piano-keyboard-only design, no staff** | **Hand-rolled keyboard** (~200 lines, zero deps, own it forever) | **`klavier`** as a reference to fork/vendor; **`react-piano`** if you want something installable today and can live with 2019-era styling | Every other keyboard package (2018–2021, near-zero adoption) |
| **Click a note on the staff to answer** | **abcjs** — `clickListener` + `selectTypes` + `add_classes` is the only first-class built-in answer | **Hand-rolled SVG** — `onClick` on a `<g>`, total control | VexFlow (no class annotations as of 5.0.0; the PR has been open since 2025-10-26 — you must overlay hit targets) |
| **Prettiest possible engraving** | **Verovio rendered at build time in Node** → ship static SVG strings, zero runtime WASM | Verovio lazy-loaded at runtime if the exercise set is open-ended and ~2.3 MB gz is acceptable | — |
| **Import real MusicXML scores** (dictation against real excerpts) | **OSMD** — exactly its job, actively maintained, BSD-3 | Verovio (better engraving, also reads MusicXML, heavier + LGPL) | abcjs (ABC-native), hand-rolling |
| **Guitar/fretboard-focused training** | **alphaTab** — tab + notation + integrated playback + Guitar Pro import | — | Everything else |
| **One library for notation AND audio** | **abcjs** (lighter, simpler, score-shaped audio, MIT) | **alphaTab** (far more capable audio, far heavier, MPL-2.0) | — |

### 5.2 Named scenarios: full stack suggestions

**Scenario 1 — MVP: pitch/interval/chord recognition only.** No rhythm, no dictation, answers by multiple-choice buttons or a keyboard.

- *Stack 1a (lightest, most control):* **raw Web Audio (thalia's engine, refactored per §3.4) + `tonal` + `smplr` + hand-rolled SVG staff with subsetted Bravura + hand-rolled piano keyboard.** ~37 KB gzip of audio/theory deps plus <20 KB of font, with zero notation dependencies and zero imperative-DOM integration bugs. This is the best fit if the author wants to keep and extend the audio layer they already built, and it defers every hard decision.
- *Stack 1b (fastest to working):* **Tone.js (`Tone.Sampler`) + `tonal` + abcjs.** ~89 KB gzip of audio plus ~500 KB of abcjs, but exercise content is a one-line ABC template literal and click-to-answer on the staff is free. Essentially `vincentxu123/chord-ear-trainer` plus a renderer.
- *Judgment:* 1a is the better fit for this author specifically, given the existing codebase and the evident interest in the audio layer; 1b is the better fit if the goal is exercise content shipped this month.

**Scenario 2 — add rhythm dictation.** Beamed eighths and sixteenths, a metronome count-in, tempo control, possibly tap-along.

- *Stack 2a:* **Tone.js + `tonal` (incl. `@tonaljs/rhythm-pattern`) + abcjs, abcjs lazy-loaded on the rhythm route only.** `Tone.Transport` removes the BPM/bar/beat arithmetic entirely and gives you `scheduleRepeat`, loop points and musical-time notation; abcjs gives automatic beaming and `clef=perc` for free. This is the lowest-effort path to a working rhythm module and matches where the prior art has converged.
- *Stack 2b:* **raw Web Audio + a ~60-line lookahead scheduler + `tonal` + `smplr` + abcjs (lazy on that route).** Keeps the bundle small and the audio layer yours; the scheduler is the one piece of real work, and it is well-documented and unit-testable. Reuse thalia's existing drum synthesis for the rhythm voices — it is legitimately good and directly applicable.
- *Either way:* keep the hand-rolled SVG staff for the pitch routes and code-split the notation engine behind the rhythm route only. That confines the one genuinely hard notation problem (beaming) to where it earns its weight. And **add latency calibration** (`ctx.outputLatency` plus a "tap along to the click" calibration screen) before shipping any tap-along mode — Bluetooth alone will otherwise ruin it.

**Scenario 3 — piano-keyboard-only UI, no staff at all.** Broadest audience, no notation literacy required.

- *Stack 3a:* **raw Web Audio + `tonal` + `smplr` + hand-rolled keyboard component.** Zero notation dependencies of any kind. ~37 KB gzip total, ~200 lines for the keyboard. This is the cheapest complete app in the document, and per §4.9 it is arguably the better *product* for most learners — no enharmonic ambiguity, visually obvious interval shape, unambiguous click input.
- *Stack 3b:* the same with **Tone.js in place of raw Web Audio + smplr**, if rhythm or tempo features are on the near-term roadmap and you would rather adopt the Transport once than write a scheduler later.
- *Optional later:* add a small hand-rolled SVG staff reveal for users who want it, as a toggle. Because the data model stays yours (MIDI numbers), adding it later costs nothing structurally.

### 5.3 The things that are not judgment calls

A short list of items where the research genuinely does point one way:

- **Adopt `tonal`**, delete `notes.ts`. 14 KB gzip, actively maintained, TypeScript-native, and it removes hundreds of lines of error-prone hand-written theory code — including the enharmonic, voicing and voice-leading logic you would otherwise never build.
- **Do not use `teoria`** (2017), **`soundfont-player`** (archived), or any published React wrapper for any notation engine or for Tone.js. All dead.
- **Do not use Howler or use-sound as the audio engine** — neither has a "play at time T" primitive. They are fine for UI dings.
- **Thread absolute `when` times through every play function from day one.** Retrofitting touches every file.
- **Ship the gesture-unlock and `'interrupted'`-recovery layer before anything else ships.** It is ~20 lines and the failure mode is silent, total, and mobile-only.
- **Use sampled instruments, not oscillators**, for the actual exercises — this is a pedagogy requirement, not an aesthetic preference.
- **Never let a notation library own your audio.** Ear training needs signal-shaped audio (pure tones, precise gaps, exact cent offsets, controlled timbre) that no notation library's MIDI synth exposes well.
- **Always render the answer as text alongside any notation**, for accessibility.
